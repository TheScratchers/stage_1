# Python Implementation — Stage 1 Data Layer

Team member: **Aimar Daniel Alejandro Santana**

This folder contains the Python implementation of the data layer: a
Project Gutenberg downloader, three alternative datalake storage
structures, two datamarts (SQLite metadata + inverted index, the
latter in three storage variants), a minimal control layer, and the
benchmark scripts used to compare the different structures - following
the shared cross-language contract in `../shared/CONTRACT.md` so the
numbers are comparable against the Java and C++ implementations.

The team's three inverted-index structures are: a single monolithic
JSON file, a hierarchical folder-per-letter/file-per-term layout, and
SQLite (a single `(term, book_id)` table, schema shared with the Java
implementation). All three languages (Python, Java, C++) use the same
3 structures, so the cross-language comparison is meaningful.

## Requirements

- Python 3.9+
- Dependencies: `pip install -r requirements.txt` (installs `requests`)

No external database or container is needed - SQLite is part of
Python's standard library.

All commands below assume the current directory is `python/`.

```

│                                        (see "Shared benchmark contract"
│                                        below; generated, git-ignored)

│   ├── inverted_index.json           ← JSON inverted index (git-ignored)
│   ├── inverted_index/               ← hierarchical inverted index (git-ignored)
│   ├── inverted_index.db             ← SQLite inverted index (git-ignored)

│                                        one file per benchmark - these are
│                                        the evidence referenced in the report)
├── control/                          ← downloaded/indexed_books.txt (git-ignored)

    CONTRACT.md                         shared with the Java and C++

```

Everything under `datalake*/`, `control/` and the `.db`/`.json` files
under `datamarts/` is generated by running the scripts below — only
the benchmark result files are committed.

## 1. Data source — download one book

```
python src/download_book.py <book_id> <output_dir>
```

Example:
```
python src/download_book.py 1342 datalake/raw_test
```

Downloads the book from Project Gutenberg and splits it into
`<book_id>.header.txt` and `<book_id>.body.txt`.

## 2. Datalake — three storage structures

Each script ingests one or more books (downloading + saving) using a
different directory layout:

```
python src/datalake.py <book_id> [<book_id> ...]        # time-based:  datalake/YYYYMMDD/HH/
python src/datalake_book.py <book_id> [<book_id> ...]    # book-based:  datalake_book/<book_id>/
python src/datalake_batch.py <book_id> [<book_id> ...]   # batch-based: datalake_batch/batch_X-Y/
```

Example:
```
python src/datalake.py 1342 5 11
```

## 3. Datamarts

### Metadata (SQLite)

```
python src/metadata.py [datalake_dir] [db_path]
```
Defaults: `datalake_dir=datalake`, `db_path=datamarts/books.db`.
Scans every `*.header.txt` file, parses title/author/language, and
stores them in SQLite.

### Inverted index — three structures

```
python src/inverted_index.py [datalake_dir] [out_path]                # single JSON file
python src/inverted_index_hierarchical.py [datalake_dir] [index_root] # folder-per-letter/file-per-term
python src/inverted_index_sqlite.py [datalake_dir] [db_path]          # SQLite (term, book_id) table
```
Defaults match the metadata script above (`datalake_dir=datalake`).

## 4. Control layer

```
python src/control.py [steps]
```
Each step either indexes one pending book or downloads a new one
(never both), tracking progress in `control/downloaded_books.txt` and
`control/indexed_books.txt`. Indexing a book updates all three
inverted-index structures (JSON, hierarchical, SQLite) incrementally,
plus the SQLite metadata table. Defaults to 1 step.

## 5. Shared benchmark contract — one-time setup

The three benchmark scripts (next section) don't use arbitrary
downloaded books - they replicate the same 20 real Gutenberg books
that Java and C++ also use (`../shared/books.txt`), so results are
comparable across languages. Those 20 books need to be downloaded once
into their own stable folder, separate from the normal `datalake/`:

```
python src/download_shared_dataset.py
```

Idempotent - safe to re-run; it only downloads whatever's still
missing from `datalake_shared/`.

## 6. Benchmarks

All three scripts take the same kind of argument - a comma-separated
list of scales (how many synthetic books to replicate the 20 real
books' content across) - and default to the contract's agreed scales.
Each prints a results table per scale to stdout, and for a scale big
enough to take a while, periodically prints a progress line
(`...processed X/N books` / `...wrote X/N books`) so a long build
doesn't look like it's hung.

```
python src/benchmark_datalake.py [scales_csv]
```
Default scales: `100,1000,10000`. Compares the 3 datalake structures:
write throughput, lookup cost, storage overhead, scalability across
scales, plus incremental-processing cost (ingesting a small new batch
on top of existing data) and recovery behavior (resuming correctly
after a simulated mid-ingestion crash). Results:
`datamarts/benchmark_datalake_results.json`.

```
python src/benchmark_inverted_index.py [scales_csv] [book_ids_csv]
```
Default scales: `100,1000,10000`. One run now benchmarks all 3
inverted-index structures (JSON, hierarchical, SQLite) together - no
separate pass or external database needed. Compares build time, query
performance (10 fixed contract words), storage overhead, scalability,
update performance (adding one book without a full rebuild), and peak
memory usage. `book_ids_csv` overrides the 20 contract books (e.g. a
single id, for a quick local smoke test) - leave it out for an
official run. Results:
`datamarts/benchmark_inverted_index_results.json` (merged by scale, so
re-running just one scale doesn't lose the others).

```
python src/benchmark_metadata.py [scales_csv]
```
Default scales: `100,1000,10000,100000` (the contract's 3 shared
scales, plus an extra 100,000-book tier specific to this benchmark, to
stress-test SQLite further). Measures insertion speed and query
performance (primary-key lookup + the 2 fixed `find_by_author`
queries) at each scale. Results:
`datamarts/benchmark_metadata_results.json`.

Note on where the benchmarks write their disposable synthetic data:
each script creates and deletes thousands of small synthetic files per
run - purely scratch, never read by anything else - in a temp
scratch folder outside this project's own tree, so a cloud-sync client
watching this folder (OneDrive, Dropbox, Google Drive, ...) never gets
in the way of cleaning it up between scales. Only the final
`benchmark_*_results.json` files (committed to git) are the actual
deliverable.

## Tests

A pytest suite covers the core logic of every module (path/structure
computations, header parsing, index build/search/update, and the
control layer's decision logic) using temporary directories and
mocks - no network access or external database needed, including for
the SQLite structure (it's exercised directly via Python's standard
library, same as the metadata datamart).

```
pip install pytest
python -m pytest tests/ -v
```

## Quick end-to-end example

```
cd python
pip install -r requirements.txt
python src/datalake.py 1342 5 11
python src/metadata.py
python src/inverted_index.py
python src/inverted_index_hierarchical.py
python src/inverted_index_sqlite.py
python src/control.py 3
```
